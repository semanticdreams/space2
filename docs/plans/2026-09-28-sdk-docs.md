# SDK Docs Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Create a first-class `docs/sdk/` documentation section for people building apps, extensions, workflows, widgets, worlds, or independent applications with Space.

**Architecture:** Add a new top-level SDK docs section using the learning-path structure from the design spec: overview, getting started, concepts, tutorials, guides, reference, and examples. Keep SDK pages consumer-facing and curated, linking to existing `docs/dev/**` internals rather than duplicating maintainer docs. This is docs-only: `docs/sdk/**` becomes the canonical builder-facing section, with home, user, developer, and VitePress navigation updates that expose it as a peer audience.

**Tech Stack:** VitePress Markdown docs, `docs/.vitepress/config.mts`, kebab-case Markdown filenames, explicit index link lists, local docs validation with `cd docs && npm run docs:build`.

## Global Constraints

- Use Option A as the initial shape: `docs/sdk/index.md`, `docs/sdk/getting-started.md`, `docs/sdk/concepts.md`, `docs/sdk/tutorials/`, `docs/sdk/guides/`, `docs/sdk/reference/`, and `docs/sdk/examples/`.
- The section should launch with skeletal but useful pages rather than waiting for perfect reference coverage.
- Each page can start as a curated entry point that links to existing examples and developer internals, then become more complete over time.
- The docs must not promise stable public API guarantees until the project explicitly decides what is stable.
- Use consumer language first: app, host, capability, runtime facet, extension, command, package.
- Define project-specific terms before using them heavily.
- Use tutorials for learning, guides for task solving, reference for lookup, and examples for copyable starting points.
- Keep SDK docs focused on contracts and usage; link to `docs/dev/` for internals, rationale, and maintenance workflows.
- Do not duplicate large blocks from existing developer docs or example READMEs.
- Use kebab-case Markdown filenames and explicit index link lists, matching current documentation conventions.
- Avoid adding compatibility aliases or legacy terminology; use canonical names only.
- Avoid promising SDK stability or versioning guarantees until that policy is decided.
- Documentation should make missing capability behavior explicit: required SDK capabilities should fail loudly rather than silently doing nothing.
- Pages that describe commands, host capabilities, runtime facets, or packaging should call out required inputs, expected failures, and where users should look for debugging information.
- Treat `docs/sdk/index.md` and each child `index.md` as canonical navigation pages.
- When new SDK pages are added, their parent index and VitePress sidebar should be updated in the same change.
- Do not make runtime or SDK behavior changes.
- Do not create new SDK examples beyond linking and curating existing examples.
- Do not move or delete existing `docs/dev/` content.
- Do not define a formal SDK stability/versioning policy.
- Do not reorganize the entire documentation site beyond adding the new SDK section and necessary navigation links.

- `docs/sdk/index.md` — SDK landing page and audience router.

- `docs/sdk/guides/index.md` — guide index with explicit child links.
- `docs/sdk/guides/app-layout.md` — recommended app repository layout.
- `docs/sdk/guides/hostable-runtime-apps.md` — `create(host) -> runtime` composition guidance.
- `docs/sdk/guides/embedded-workspace-hosting.md` — embedded host and teardown guidance.
- `docs/sdk/guides/graph-extension-units.md` — graph extension unit authoring guidance.
- `docs/sdk/guides/ui-surfaces.md` — SDK-facing UI surface guidance.
- `docs/sdk/reference/index.md` — reference index with explicit child links.
- `docs/sdk/reference/app-module-contract.md` — hostable app module shape and invariants.
- `docs/sdk/reference/host-capabilities.md` — host capability lookup page.
- `docs/sdk/reference/runtime-facets.md` — runtime facet lookup page.
- `docs/sdk/reference/commands.md` — command metadata, payload, and failure lookup page.
- `docs/sdk/reference/scene-capability.md` — scene capability lookup page.
- `docs/sdk/reference/packaging-workflow.md` — reusable package workflow inputs and failures.
- `docs/sdk/reference/graph-extension-descriptors.md` — graph extension descriptor fields and invariants.
- `docs/sdk/examples/index.md` — curated example index, initially Snake.
- `docs/index.md` — home page action for SDK docs.
- `docs/user/index.md` — user-to-SDK audience boundary cross-link.
- `docs/dev/index.md` — developer-to-SDK audience boundary cross-link.
- `docs/.vitepress/config.mts` — top navigation and `/sdk/` sidebar.

- `docs/sdk/` exists with the complete structure named in this plan.

- `docs/sdk/index.md`, `docs/sdk/tutorials/index.md`, `docs/sdk/guides/index.md`, `docs/sdk/reference/index.md`, and `docs/sdk/examples/index.md` explicitly link to their child pages or curated entries.

- Existing `docs/dev/**` content is not moved, deleted, or copied wholesale.
- `cd docs && npm run docs:build` passes locally.
- PR CI remains the full integration gate before ready-to-merge claims.
